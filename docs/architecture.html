Architecture

A static site with a pure DSP core. The interesting decisions are about where the browser is allowed to appear and how audio gets asserted without a microphone.

Shape of the thing

There is no framework, no bundler and no runtime dependency. package.json exists only so npm run serve and npm test are available and so Node treats the folder as ESM; nothing is installed. The delivered artifact is the folder itself.

That constraint is the whole architecture. Every piece of audio work is a plain function in its own module under js/, taking buffers and returning buffers. The browser appears in exactly two files:

  • js/capture.js — getUserMedia, MediaRecorder, and a ScriptProcessorNode fallback for capture.
  • js/app.js — the only DOM layer, owning ids, project state, playback through one AudioContext, and the export flow.

No module under js/ imports from app.js. The direction is always page to module, never sideways into the UI.

js/contract.md and js/contract-appendix.md are the written interfaces these were built against, including the parameter ranges the tests rely on. They are checked in, so a change to a signature is visible in the diff rather than in a runtime surprise.

The purity rule

Modules must import and run under bare Node with no shims. Browser globals are legal only inside functions, never at import time, so a test can load any module without a DOM stub.

Functions return their results and never mutate an input buffer in place, with two named exceptions whose prefixes say so: applyEQ, compress, limit and normalizeRms may return fresh buffers but must not alias the input. Numbers stay finite; divide-by-zero is guarded and silence returns a zero pitch rather than NaN.

Sample rate is a parameter everywhere. Nothing assumes 44.1 kHz, which is why the default is 48 and why a project carries its rate with it.

Testing audio without a room

The suite builds a 2.4 second synthetic phrase: four syllables at known MIDI pitches with a shaped envelope and a little noise. It then asserts the pipeline end to end — four notes detected, each within two semitones and 120 ms of its source, every note landing in key after a full snap, the input array unchanged by the snap, the WAV header byte-correct, every output sample finite, no sample above 0 dBFS.

Preferences would make a weak suite. The phrase is deterministic, so the assertions are equalities and ranges rather than vibes. Each module also carries a self-test that the suite spawns and requires to print ALL CHECKS PASSED; a module can be verified on its own in one command.

What this does not cover: a real microphone, and playback scheduling. Both are listed as gaps rather than pretended away.

Serving

scripts/serve.mjs is forty lines of node:http: path normalization, MIME by extension, no-store, a 403 for anything that escapes the root. Loopback only. It exists for the tests and for people who do not want to look up a Python one-liner, not because the app needs a backend.

The CI job runs the same server, so the served-site checks are exercised on every push rather than only on a laptop.

Failure modes worth knowing

  • file:// breaks module loading. The folder must be served.
  • A microphone on a non-secure origin is refused by the browser; loopback counts as secure.
  • The compressor and limiter are sample loops in JS. A five minute take is slow to render, and the UI stays synchronous while it does.
  • Everything is mono until the master stage, which duplicates the channel. True stereo take handling does not exist yet.
